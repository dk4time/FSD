Sections 1 and 2: the problem and the ground rules

@ 3:30 · ~2.5 min
OPENP1_Product_Catalog.pdf
SHOWPage 1, sections 1 and 2. Highlight “in memory only”, “empty”, “PORT” and “Restart your server”.
SAY

Section 1 says: build a REST API for products. You may use Express or Spring Boot. There is no starter code.

Now read this line slowly: data is kept in memory only. That means an array in Express, or a List in Java. No database, no JSON file and no sample data. When your server starts, the list must be empty.

Why empty? Because the evaluator creates its own records. It calls your POST endpoint about 45 times with random values. If your server already has data, the counts will be wrong and you lose marks.

Section 2 has five rules. Rule 2: read the port from the PORT environment variable, and use 8080 if it is not set. Rule 3: every request and response is JSON. Rule 4: restart your server before every evaluation, so it starts empty again. Rule 5: do not change any field name, path or status code. The evaluator checks them letter by letter. “Products” with a capital P is wrong. “product” without the s is wrong.

Section 3: the resource table, row by row

@ 6:00 · ~4 min
OPENP1_Product_Catalog.pdf
SHOWPage 1, section 3 table. Point to each row while you speak. Then the two sample JSON blocks below the table.
SAY

This table is the heart of the paper. Each row is one field. The columns tell you the name, the type, the rules and whether it is required. Every rule you see here becomes one check in your code.

First row: id. Your server creates it. Never take id from the request body. A simple counter, 1, 2, 3, is enough.

name: a string. Trim it first, which means remove the spaces at the start and end. After trimming it must be 3 to 60 characters. It is searchable and sortable; remember these two words, we use them in section 5.

brand: a string, trimmed, 2 to 40 characters, searchable.

category: an enum. That means only these five values are allowed: Electronics, Books, Clothing, Home, Sports. It is case-sensitive, so “electronics” with a small e is invalid.

price: a number, greater than 0, at most 100000, decimals allowed. Important: it must be a JSON number. If someone sends price as text, in quotes, it is invalid.

stock: an integer, a whole number from 0 to 10000. So 1.5 is invalid.

inStock: a boolean, true or false. Again, a real JSON boolean. The text “true” in quotes is invalid.

Below the table: unknown fields are ignored. If someone sends a colour field, you do not store it and you do not return it.

And here are two samples. The first is what the client sends with POST. The second is what your server returns: the same fields, plus the id your server created.

Section 4: the six endpoints

@ 12:30 · ~2 min
OPENP1_Product_Catalog.pdf
SHOWPage 1, section 4 table, then the three bullet points under it.
SAY

Section 4 lists six endpoints, all under /api/products.

POST /api/products creates a record and returns 201 with the created record. GET /api/products returns the list. GET /api/products/ with an id returns one record. PUT replaces a record. PATCH updates some fields. DELETE removes a record and returns 204 with an empty body.

Now the three bullet points. PUT replaces the whole record, so every required field must be sent. And PUT never creates a record: if the id does not exist, return 404.

PATCH changes only the fields you send, but at least one field must be sent. An empty object is 400. Every field you send is checked with the same rules as POST.

And the id can never change. Even if the body contains an id, you ignore it.

Section 5: the list, pagination, filters, search and sort

@ 14:30 · ~4 min
OPENP1_Product_Catalog.pdf
SHOWPage 1, section 5 table, then “How a list request is processed”, then the list response JSON. Then page 2, the yellow “Short on time? Minimum list.” box.
SAY

Section 5 explains GET /api/products. The list response is not a plain array. It is an object with five keys: data, page, limit, total and totalPages. data holds the records for this page.

page and limit are the pagination. Default page is 1, default limit is 10, and limit can be at most 50. Anything that is not a positive whole number is 400. But a page after the last page is not an error. It returns 200 with an empty data array.

search looks inside name or brand, ignoring capital and small letters. category and inStock are exact filters. minPrice and maxPrice are a range, and both ends are included. sort can be name, price or stock, and order can be asc or desc. Any value you do not support, like sort equals banana, is 400.

Now this line is very important: filters, then search, then sort, then pagination. Let me give an example. Say there are 45 products. You ask for category Electronics, and 9 of them match. You ask for limit 5, page 2. So page 2 shows records 6 to 9, that is 4 records. total is 9, not 45 and not 4. totalPages is 9 divided by 5, rounded up, which is 2.

And if you do not sort, return the records in the order they were created, oldest first.

Now look at this yellow box on page 2. It says: short on time? Even if you cannot finish pagination, filters, search and sort, still return this shape: the first 10 records, page 1, limit 10, the total and totalPages. This alone gives you the List basics marks. The other 60 marks do not depend on these four features. Never return a bare array.

Section 6: errors, and the rules that are easy to miss

@ 18:30 · ~3 min
OPENP1_Product_Catalog.pdf
SHOWPage 2, section 6 table, the “Validation” paragraph, then the 12 “Rules that are easy to miss”.
SAY

Every error must be JSON, with a short message under the key error or message. The wording is free. Nobody checks your sentence. But the status code is checked exactly.

Remember the five codes: 201 created. 200 read, list or update. 204 deleted. 400 for anything invalid: a bad body, a bad field, broken JSON or a bad query parameter. 404 for an unknown id or an unknown route. And 409 for a duplicate unique value, which P1 does not have.

Now the twelve rules that are easy to miss. I group them into four ideas.

Idea one: unknown things are 404. An id that does not exist is 404, even if it looks strange, like abc. Never 400 and never 500. PUT on an unknown id is 404. Delete twice, and the second time is 404. An unknown route is a JSON 404.

Idea two: types are strict. A number sent as text is invalid. true sent as text is invalid. 1.5 for stock is invalid. Price 0 or negative is invalid. Text is trimmed before checking and before saving.

Idea three: the server owns the id. POST ignores the id you send. PUT and PATCH never change it.

Idea four: some things look like errors but are not. A page after the last page is 200 with empty data. minPrice greater than maxPrice is 200 with empty data and total 0.

Finally: your server must never crash and never return an HTML error page, even for broken JSON.

Sections 8 and 10: how you are marked

@ 21:30 · ~2.5 min
OPENP1_Product_Catalog.pdf
SHOWPage 2, section 8 bullets and the “Suggested build order” line. Then page 3, the section 10 marking scheme table.
SAY

The evaluator starts with your empty server. It creates its own random records with POST. Then it runs 100 checks, in a fixed order, 1 mark each. There are no part marks inside a check.

It looks only at HTTP: the status code, the JSON shape and the values. It does not look at your code, your folders or your framework. Express and Spring Boot are marked exactly the same.

Two warnings. If POST does not work, most other checks cannot even run, because they need records. So build and test POST first. And if your server crashes in the middle, every check after the crash fails.

Now the marking scheme on page 3. Create 14, Read one 8, List basics 8, PUT 10, PATCH 10, DELETE 8, HTTP basics 2. That is 60 marks for the basic CRUD work. Pagination 12, Filter 10, Search 8, Sort 6 and Combined 4 give the other 40.

So the build order in the paper makes sense: POST and GET by id, then the list, PUT, PATCH and DELETE. Then pagination, filters, search and sort. Then go through the easy-to-miss rules.

14  // ---------- validation helpers ----------
15  function isPlainObject(v) {
16    return v !== null && typeof v === 'object' && !Array.isArray(v);
17  }
18  
19  // Each checker returns { value } when valid or { error } when not.
20  function checkText(body, field, min, max) {
21    const v = body[field];
22    if (typeof v !== 'string') return { error: `${field} must be a string` };
23    const t = v.trim();
24    if (t.length === 0) return { error: `${field} must not be blank` };
25    if (t.length < min || t.length > max) return { error: `${field} must be ${min} to ${max} characters` };
26    return { value: t };
27  }
28  
29  const validators = {
30    name: (b) => checkText(b, 'name', 3, 60),
31    brand: (b) => checkText(b, 'brand', 2, 40),
32    category: (b) => {
33      if (typeof b.category !== 'string' || !CATEGORIES.includes(b.category)) {
34        return { error: `category must be one of ${CATEGORIES.join(', ')}` };
35      }
36      return { value: b.category };
37    },
38    price: (b) => {
39      const v = b.price;
40      if (typeof v !== 'number' || !Number.isFinite(v)) return { error: 'price must be a number' };
41      if (v <= 0) return { error: 'price must be greater than 0' };
42      if (v > 100000) return { error: 'price must be at most 100000' };
43      return { value: v };
44    },
45    stock: (b) => {
46      const v = b.stock;
47      if (typeof v !== 'number' || !Number.isInteger(v)) return { error: 'stock must be a whole number' };
48      if (v < 0 || v > 10000) return { error: 'stock must be from 0 to 10000' };
49      return { value: v };
50    },
51    inStock: (b) => {

SAY

Here is the validation. Put the section 3 table next to it and you will see they match row by row.

checkText, lines 20 to 27, is used for both text fields. It checks that the value is a string, trims it, rejects a blank value, and checks the length. It returns the trimmed value, so we store the trimmed text, as rule 2 asks.

Then the validators object. name is checkText with 3 and 60. brand is checkText with 2 and 40. category must be one of the list, and includes is case-sensitive, so “electronics” fails.

price, lines 38 to 44: typeof must be number. So the text “799.5” fails here. Then it must be greater than 0 and at most 100000.

stock uses Number.isInteger, so 1.5 fails. Then 0 to 10000. And inStock must be typeof boolean, so the text “true” fails.

Each checker returns either a value or an error. That keeps the next part simple.

validateBody, findIndex and toRecord

@ 31:30 · ~3 min
OPENexpress/P1_products/server.js
SHOWLines 58 to 91.
express/P1_products/server.js · lines 58–91
58  // partial = true for PATCH: only validate the fields that were sent.
59  function validateBody(body, partial) {
60    if (!isPlainObject(body)) return { error: 'Request body must be a JSON object' };
61    const clean = {};
62    let sent = 0;
63    for (const field of FIELDS) {
64      if (!(field in body)) {
65        if (partial) continue;
66        return { error: `${field} is required` };
67      }
68      sent++;
69      const r = validators[field](body);
70      if (r.error) return { error: r.error };
71      clean[field] = r.value;
72    }
73    if (partial && sent === 0) return { error: 'Send at least one field to update' };
74    return { value: clean };
75  }
76  
77  function findIndex(id) {
78    return products.findIndex((p) => String(p.id) === id);
79  }
80  
81  function toRecord(id, data) {
82    return {
83      id,
84      name: data.name,
85      brand: data.brand,
86      category: data.category,
87      price: data.price,
88      stock: data.stock,
89      inStock: data.inStock,
90    };
91  }
SAY

validateBody is used by POST, PUT and PATCH. The flag partial is false for POST and PUT, and true for PATCH.

First, line 60: the body must be a JSON object. Then we loop over our six known fields. If a field is missing: for POST and PUT that is an error, “name is required”. For PATCH we just skip it. Every field that is present is checked by its validator. Line 73: for PATCH, if nothing was sent, that is 400.

Notice that we only loop over known fields. So an unknown field, or an id inside the body, is simply never copied. That is how “unknown fields are ignored” and “POST ignores the id” are handled, without any extra code.

findIndex, line 77, compares the id as a string. So /api/products/abc does not crash. It just finds nothing, and we return 404.

toRecord builds the record with the id first and only the six fields. Every response uses it, so every response has the same shape.

 94  // Returns a number or null when the text is not a positive whole number.
 95  function parsePositiveInt(text) {
 96    if (typeof text !== 'string' || !/^\d+$/.test(text)) return null;
 97    const n = Number(text);
 98    return n >= 1 ? n : null;
 99  }
100  
101  function parseNumber(text) {
102    if (typeof text !== 'string' || text.trim() === '') return null;
103    const n = Number(text);
104    return Number.isFinite(n) ? n : null;
105  }
106  
107  function badRequest(res, message) {
108    return res.status(400).json({ error: message });
109  }
110  
111  // ---------- routes ----------
112  app.post('/api/products', (req, res) => {
113    const r = validateBody(req.body, false);
114    if (r.error) return badRequest(res, r.error);
115    const record = toRecord(nextId++, r.value);
116    products.push(record);
117    res.status(201).json(record);
118  });
SAY

parsePositiveInt accepts only digits, and the number must be at least 1. So page=0, page=-1 and page=abc all return null, and we will send 400. parseNumber is used for minPrice and maxPrice. badRequest sends 400 with a JSON error.

Now POST, lines 112 to 118. Only four steps. Validate the body; if there is an error, send 400. Build the record with the next id. Push it into the array. Send 201 with the record.

This is the first endpoint you should build on assessment day, because almost every check needs it.
